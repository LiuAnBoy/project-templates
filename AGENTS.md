# Project templates

This repository holds standalone starter templates for web frontends (Next.js, Vite) and backends (NestJS on Fastify, Fastify, FastAPI), plus a monorepo workspace and `monorepo.sh`, the one command that composes them into a project. Each template is a complete directory under `templates/` that runs alone, so one `curl | tar` can fetch it. `README.md` (Traditional Chinese) explains usage to the people who start projects.

## Layout

- `source/`: the layers that templates and overlays are built from. Layers are shared files plus an optional `package.fragment.json` that contributes to the generated `package.json`. Web layers: `web/common`, `web/<next|vite>` (each with its `Dockerfile`, web compose block and `env.fragment`, and Vite's `nginx/default.conf.template`), `ui/plain` (what a base without a UI library needs: its `UiProvider`, `useNotification` and documents), and per UI library `ui/<antd|mui|heroui>/common` plus an optional `ui/<lib>/<next|vite>` for files that must differ in one framework. Server layers: `server/common` (all three backends, with the store-neutral `docs/rules/data.md`), `server/node` (the two Node backends, with their `Dockerfile` and server compose block) and `server/<nest|fastify|fastapi>` (`server/fastapi` also holds its own `Dockerfile` and server compose block). Docker layers: `docker/main` (the main compose block and its header, `.dockerignore`, the `## Docker` block of `AGENTS.md`, `docs/rules/docker.md` with its index fragment, and the `COMPOSE_PROJECT_NAME` line of `.env.example`), listed in every template recipe but `workspace` after the framework's layers and before `data/none`, and `docker/web` (the `env.fragment` a web base adds: `DOCKER_API_HOST` and `WEB_PORT`), listed in the `next` and `vite` recipes after `docker/main`. `docker/monorepo` holds what only a composed root needs and is listed in no recipe: `main` (the root main block with the `edge` network, its `.dockerignore` and the env block), `dashboard` (the `DASHBOARD_PORT` line), `web-next` and `web-vite` (a web block and a Dockerfile each, written for a part named by `PART`, and Vite's nginx template that resolves its upstream through Docker's DNS) and `server-node` and `server-fastapi` (the server block, and for Node the Dockerfile); `monorepo.sh` joins them through `docker-blocks.mjs`. Data layers: `data/none` (what a base with no store says: its `AGENTS.fragment.md` block and `database.fragment.md`; the last layer of every backend recipe, left out of every data overlay), `data/compose` (the main compose block: the header of `docker-compose.dev.yml`), `data/integration/<framework>` (the integration test config and the guard that refuses a non-local host), `data/sql/node` (the port, the migration journal and its reporting, which every SQL store on Node shares, and the Docker side of migrating: the `migrate` service block, the fragment that makes `server` wait for it, and the runtime fragment that copies `scripts/` and `drizzle/`), `data/<store>/{common,node,<framework>}` (a store's settings, compose block, rule page, `src/db/database.ts` or `src/redis/client.ts`, and fragments), `data/redis/alone` (the heading and notes a project whose only store is Redis needs, because a database store would have brought them) and `data/wiring/<framework>/<database|redis|database-redis>` (the seam files that call the stores' factories; the last layer of an overlay). `data/sql/fastapi` holds the Alembic environment, the migration commands and the port every SQL store on FastAPI shares, with the same Docker side (copying `scripts/`, `alembic/` and `alembic.ini`), and `data/<store>/fastapi` a store's `src/db/database.py` (or `src/redis_client/client.py`), its rule page and its tests. Each server store's `common` layer holds a `compose.server.fragment.yml` (how the service reaches `server`); `data/postgres/common` also holds `docker-compose.postgres-cluster.yml`, the plain file that switches to a shared server. SQLite's `common` layer holds its named volume, a runtime fragment that creates the data directory for uid 1000 and a `dockerignore.fragment`, and `data/sqlite/node` the build fragment with the toolchain `better-sqlite3` compiles with. Recipes use the frameworks `nest`, `fastify` and `fastapi` and the stores `postgres`, `sqlite`, `mysql` and `redis`. Workspace layers: `workspace` (the root with the `contract` package) and `workspace-no-contract` (the root for a server that has no contract package).
- `templates/`: generated standalone templates, committed. `next` and `vite` are the web bases; they have no UI library, and their `shared/providers/UiProvider.tsx` and `shared/hooks/useNotification.ts` are small dependency-free versions that an overlay replaces. `nest`, `fastify` and `fastapi` are the backends, each with a `src/infra/` seam (no checks, no shared limiter store, no settings) that a data overlay replaces, so a base needs no store; `workspace` is the monorepo root. Every template but `workspace` has a `Dockerfile`, a `docker-compose.yml` and a `.dockerignore`.
- `overlays/`: generated overlays, committed. The six UI overlays (`next-antd`, `next-mui`, `next-heroui`, `vite-antd`, `vite-mui`, `vite-heroui`) hold only the files of their own layers plus a full `package.json` (the base and the library merged, named after the base), their `pnpm-lock.yaml`, and the joined `.env.example`, `AGENTS.md` and `docs/README.md` (the first and the last equal their base's). They hold no Docker file, so their base's stand. Each is extracted over a fresh base once, when a project is created: there is no installer and no merge, only overwriting. The nineteen data overlays, `<framework>-<store>`, `<framework>-<store>-redis` and `<framework>-redis` for the frameworks `nest`, `fastify` and `fastapi` and the stores `postgres` and `sqlite`, and `mysql` on `nest` and `fastify` alone (for example `nest-postgres-redis`), are built the same way from the layers `recipes.mjs` lists; each also holds the joined `.env.example`, `AGENTS.md`, `docs/README.md` and `docs/database.md`, `docker-compose.dev.yml` when a store is a server, and the whole-project `docker-compose.yml`, `Dockerfile` and `.dockerignore` when one of its own layers contributes to them (a server store's compose fragment, a SQL store's `migrate` block and runtime fragment, SQLite's volume and ignore lines). The PostgreSQL overlays also hold `docker-compose.postgres-cluster.yml`. `workspace-no-contract` is the one overlay of neither kind: the root of a monorepo whose server is FastAPI. It replaces the root manifest, the workspace file, `AGENTS.md` and `docs/README.md` of `workspace` so they state only what exists, and it is applied only by `monorepo.sh`; keeping it under `overlays/` keeps it out of a standalone `workspace` fetch.
- `scripts/`: the tooling below.
- `monorepo.sh`: the composer (see "monorepo.sh").
- `README.md`: usage for the people who start projects, in Traditional Chinese.
- `VERSIONS.md`: the generated record of every direct dependency, its pinned version, the templates using it and the date verification last passed.
- `todos/`: local work notes, gitignored.

Never edit `templates/`, `overlays/` or `VERSIONS.md` by hand; a hand edit is overwritten by the next render or generation, and `render.mjs --check` fails on it.


## Flow for any change

1. Edit `source/` (or `scripts/recipes.mjs` when the layers of a template or overlay change). `recipes.mjs` also generates the data overlays from its lists `DATA_FRAMEWORKS` and `DATA_STORES`, which a store's `frameworks` trait narrows: an entry is named `<framework>-<store>`, `<framework>-<store>-redis` or `<framework>-redis`, so the base is the part before the first dash, and its layers run in a fixed order (the compose block when a store is a server, the framework's integration layer, each store's layers, the wiring layer last). `DATA_LIVE` names the data overlays that run against real services, and `test-render.mjs` fails when a layer of a data overlay is in none of them. `DOCKER_LIVE` names the targets `check-docker.sh` builds (the templates and the UI overlay named outright, then `nest` and `fastapi` with each database store), and `test-render.mjs` fails when a layer holding a Docker fragment is in none of them.
2. `node scripts/render.mjs [--only a,b]` regenerates `templates/` and `overlays/`. It copies layers in order, deep-merges the `package.fragment.json` files into a generated `package.json`, never copies a fragment, keeps an existing `pnpm-lock.yaml` or `uv.lock`, and removes stale files. Its header comment is the full list of joins; the rules are these:
   - A template's `package.json` is named after the template. An overlay copies only its own layers, but its `package.json` merges the fragments of its base template's layers and its own, and is named after the base so the project can extend it as its own. An overlay entry in `recipes.mjs` that replaces its base's manifest and documents outright (`workspace-no-contract`) names `fragmentLayers` and `agentsLayers` itself, and then only those layers contribute.
   - Five text files are joined from the fragments of the `agentsLayers` (a template's layers, or an overlay's base layers without `source/ui/plain` and `source/data/none`, then its own), in layer order, one blank line apart: `AGENTS.fragment.md` into `AGENTS.md`, `env.fragment` into `.env.example`, `database.fragment.md` into `docs/database.md`, `docs-index.fragment.md` into `docs/README.md` and `Makefile.fragment` into `Makefile`. A layer's own copy of such a file is still copied when no layer has a fragment, and a file is never both. Each `AGENTS.fragment.md` is a block with its own `## ` heading, no heading repeats across layers, and the joined result must read as one document.
   - Three more fragments edit a file that a base layer owns, found in the last of the `fragmentLayers` that holds it. Each is written only when a layer has entries and fails the render when the file has an unexpected shape: `pyproject.dependencies` (one exact pin per line) is inserted, sorted, into `[project] dependencies` of `pyproject.toml`, and a package already listed fails; `pnpm-allow.fragment` (one package name per line) is merged, sorted, into `onlyBuiltDependencies` of `pnpm-workspace.yaml`; `prettierignore.fragment` (one pattern per line) is appended to `.prettierignore`.
   - `compose.fragment.yml` blocks from an overlay's own layers are joined by section into `docker-compose.dev.yml`, and no file is written when no layer has one. The first block is the main block, whose leading comment is the file header. Every other block is a valid compose file whose only top-level keys are `services` and `volumes`, with no `name:`, `container_name`, `restart` or `build`, so blocks stay portable. The output is the header, the `name:` line that reads `COMPOSE_PROJECT_NAME` (the join alone writes it), one `services:` holding every block's services in layer order, then one `volumes:`. Any other top-level key, or a service or volume named twice, fails the render.
   - The Docker files are joined by `docker-blocks.mjs` from the `agentsLayers` and written by an overlay only when one of its own layers contributes. `docker-compose.yml` takes the store blocks, the app blocks (`compose.app.fragment.yml`: the main block, which has no `services` key, and the services, which may set `build` and `restart`) and the contributions of `compose.server.fragment.yml`, which add `environment`, `depends_on` and `volumes` lines to `server` and `migrate` and a top-level `volumes` entry, with a service's dependency on itself dropped. `Dockerfile.build.fragment` and `Dockerfile.runtime.fragment` fill the marker lines of the Dockerfile a base layer owns, and `dockerignore.fragment` is appended to `.dockerignore`. A fragment is never copied; its rules are in the header of `docker-blocks.mjs`. A server store ships its `compose.server.fragment.yml`.
3. `bash scripts/lock.sh [--data] <name>...` regenerates the lockfile whenever dependencies changed. Direct dependencies are pinned to exact versions. For an overlay it copies the base to a temp directory, extracts the overlay over it, locks both together there, and stores the result in `overlays/<name>/`: `pnpm-lock.yaml` over a Node base, `uv.lock` over a Python base. `--data` adds every data overlay that `recipes.mjs` generates to the names. `workspace-no-contract` has no dependencies and no lockfile.
4. Verify (below). A change is done only when every check passes.

`node scripts/render.mjs --check` renders every template and overlay to a temp directory and compares with `templates/` and `overlays/` (lockfiles excluded); it fails and lists each missing, extra or changed file. `--only` takes template and overlay names alike.

Updating dependency versions follows the same flow: `node scripts/outdated.mjs` reports direct dependencies in four groups (security advisories, majors, minors and patches, and updates blocked by a peer range, leaving out releases younger than 7 days unless they fix an advisory); edit the fragments, render, lock, verify.

## Verification

Run these from the repository root. Each of the first three accepts template names, or directory paths (anything containing a slash or naming an existing directory is checked where it stands, so an extracted archive or a composed monorepo works).

- `bash scripts/check-template.sh <name>...` copies the target to a temp directory, installs from the lockfile, and runs the quality scripts.
- `bash scripts/live-check.sh <name>...` starts the target and asserts its behaviour. A server with required settings cannot start from an empty environment, so `LIVE_DOTENV` (a file copied to `.env` in the temp copy) and `LIVE_PREPARE` (a command run there before the start, such as a migration) start it from its own `.env` instead; the check of `TRUST_PROXY` and `RATE_LIMIT_MAX` is then left out.
- `node scripts/check-docs.mjs <name>...` checks documents and required paths. A composed monorepo is checked part by part: `web/`, `dashboard/` when present, and `server/`, each as its own template type, plus the root documents, and `contract/` needs only its `package.json`.
- `bash scripts/make-archive.sh <out.tar.gz>` writes a codeload-shaped archive (top folder `project-templates-master/`) of the files from `git ls-files -co --exclude-standard`, so uncommitted work is included and ignored files are not.
- `bash scripts/check-overlays.sh [--static | --docker] <overlay>...` builds that archive (or reads the one named by `ARCHIVE`), extracts the base into an empty directory with `tar -xz --strip=2 project-templates-master/templates/<base>`, enters it, extracts the overlay over it with `tar -xz --strip=3 project-templates-master/overlays/<overlay>`, and runs the checks against the result. It is the only check of an overlay, because an overlay is not a project until it is applied. A UI overlay gets the three checks above. A data overlay (its base is `nest`, `fastify` or `fastapi`) gets `check-template.sh` and `check-docs.mjs`, then `check-store.sh` when it is in `DATA_LIVE`, because an empty-environment `live-check.sh` cannot start it. `--static` runs only `check-template.sh` and `check-docs.mjs`, so it starts nothing and needs no Docker. `--docker` extracts the same way and runs only `check-docker.sh` on the result, under the overlay's own heading; it cannot be combined with `--static`.
- `bash scripts/check-store.sh <dir> [label]` runs what only a real store can prove, in a temp copy of an extracted data overlay. It writes `.env` from `.env.example` with the ports moved to 15432 (PostgreSQL), 13306 (MySQL) and 16379 (Redis), starts the compose services with `up --wait` under a unique project name and tears them down with `down -v`, then runs the store tests (`pnpm test:integration`, or `make test-integration` on FastAPI), for a project with a `db:pull` script the adoption of a legacy table that holds rows (`db:pull`, then `db:generate` writing nothing, a new table generated and migrated, the legacy table's structure and rows unchanged and the baseline recorded), a migration lifecycle on a throwaway table, an empty-environment refusal and a refusal of each malformed connection URL, a boot through `live-check.sh`, each store down at startup (with a database stopped, `db:status` and `db:migrate` also fail and print no URL, password or `localhost`), and each store stopped and restarted under a running server. Its header comment lists the steps and the contract an overlay's layers meet. A SQLite-only overlay has no compose file and skips the steps that need a service.
- `bash scripts/check-docker.sh <name-or-dir>...` builds a project's images and runs them under a unique project name, in a temp copy, for a template name, an overlay name or a directory. It writes `.env` from `.env.example` with every `*_PORT` value moved up by 20000 (the server on 28000, the web port on 23000, a dashboard on 23001, PostgreSQL on 25432, MySQL on 23306, Redis on 26379) and the port of `DOCKER_API_HOST` with them, so it needs none of the ports the other checks use, and plants `SENTINEL_SECRET` in `.env`, sentinel files in `todos/` and `node_modules/`, and one migration that creates a probe table. It asserts that a blank `COMPOSE_PROJECT_NAME` is refused naming the variable, that every running service is healthy, that the user is not root, and that the sentinel, `.env`, `todos/` and the planted files are absent from `docker history`, `Config.Env`, the exported filesystem and the exported `build` stage. A project with a `server` also gets `/api/health` read exactly from inside it, hello through the published port, a malformed setting that stops the container naming the setting and no value, and the sentinel seen by `server` at runtime. A project with a database store also gets these: `server` and `migrate` carry empty `TEST_*` URLs and an empty store root password; `migrate` exited 0 and its table is in PostgreSQL or MySQL, or on SQLite its file belongs to uid 1000 in the named volume and `server` answers again after a restart; each store service stopped in turn makes `server` exit non-zero within its bound, naming the store and printing no password, URL or host and port; the switch to a shared server (a throwaway network and PostgreSQL) changes four `.env` lines and no other file, leaves no local `postgres` container, lands `migrate`'s table in the throwaway database, and restoring `.env` brings the local service back, a blank network being refused naming its variable; and with the PostgreSQL or MySQL password changed behind its volume, `up` exits non-zero, `server` stays unstarted, and `migrate`'s output holds no host, user, database name or password. A web base has no `server`: `/` answers 200 through the web port, the web container's whole environment is read and holds no sentinel, and a Vite project also answers a deep link with `index.html` and `/api/v1/hello` from a stub the script runs on the host at 28000, reached through `host.docker.internal`. That stub cannot separate a fixed `proxy_pass` from one resolved at run time, because Docker Desktop's own DNS answers `host.docker.internal` too. A composed monorepo directory (a `server/` beside a root `docker-compose.yml` and no root `Dockerfile`) is checked at its root: the lockfile is written in the temp copy with `pnpm install --lockfile-only`, each part gets its own `.env`, `todos/` and `node_modules/` sentinels, hello goes through every web port, every part's image and build stage is scanned, and with the `edge` network `server` publishes no port, two forged visitors through each web part get separate rate-limit buckets under `RATE_LIMIT_MAX=3` (200 200 200 429, then 200), and a peer on the default network, off `edge`, forging a new address per request still gets 429 on its fourth. Every Docker command runs under a bound, and a timeout is a failure naming the step. Its header comment lists the steps and the contract a project's files meet.
- `node scripts/test-render.mjs`, `node scripts/test-check-docs.mjs` and `node scripts/test-versions.mjs` test the tooling itself with fixtures and injected data, without network.
- `bash scripts/verify.sh` is the whole verification and the only gate of a finished change. It checks the syntax of every script, runs `render.mjs --check` and the three tooling tests, builds the archive, runs `check-overlays.sh` for the six UI overlays and then for every data overlay one at a time, extracts every template with the README's tar flags into an empty directory and runs the three checks there, then runs `git init` there and asserts `git check-ignore .env`. It then runs `monorepo.sh` against the archive for five compositions: `next antd nest`, `vite plain fastapi`, `next plain nest --dashboard next antd`, `next plain fastify --data sqlite` and `vite plain fastapi --data postgres,redis`. Each installs, runs `check-docs.mjs` and `pnpm typecheck`, then starts both sides and curls `/api/v1/hello` through each web port with the whole envelope asserted. A composition with `--data` first does what the printed next steps say: copies `server/.env.example` to `server/.env`, starts the compose file with the command its own header prints (which must name the project) on the ports 15432 and 16379, and migrates; its compose project is dropped afterwards. The first composition also gets a page and a Nest handler, written into the composed copy only, that import `@app/contract` at runtime. It proves `monorepo.sh` refuses unknown values, a bad name, an existing target, an empty `--data`, a repeated `--no-docker` and every `--data` choice outside the seven it accepts, `fastapi` with `mysql` included, each with exit 2 and without writing anything, and that a composition made with `--no-docker` holds none of the Docker files. Its Docker step runs `check-docker.sh` on every target of `DOCKER_LIVE` and then on three compositions made with `monorepo.sh`: `next plain nest --dashboard vite plain --data postgres,redis`, `vite plain fastapi --data sqlite` and `next plain fastify --data sqlite`; the composed directories are checked at their root, and the step uses only the moved ports 23000, 23001, 28000, 25432, 23306 and 26379. On a pass its last step is `node scripts/versions.mjs --stamp`, which regenerates `VERSIONS.md` and sets its verification date to today (`node scripts/versions.mjs --check` exits 1 when the file is stale). It needs network access, and ports 8000, 13306, 15432 and 16379 and each composition's web ports free.

### Exit codes of a check that needs Docker

`check-store.sh`, `check-docker.sh` and `check-overlays.sh` exit 0 only when every check ran and passed, 1 when a check failed, and 3 when a check that needs a service could not run because the `docker` binary is absent or its daemon does not answer. Exit 3 is incomplete, never a pass: `check-store.sh` prints `INCOMPLETE <overlay>: needs Docker; no real-store check ran`, `check-docker.sh` prints `INCOMPLETE <target>: needs Docker; no image was built` for each target, and `check-overlays.sh` runs its static checks first, carries the 3 once every overlay has run, and exits 1 instead when any overlay failed. A failed image pull, a Docker command that outlasts its bound, or a failed assertion is a 1. `verify.sh` follows it too: it runs `check-docker.sh` on each Docker target and composition one at a time, counts every exit 3 as incomplete and stops at any other failure, finishes its other steps, prints `INCOMPLETE verify: <n> overlays not checked against real services` as its last line, exits 3 and does not stamp `VERSIONS.md`. Any later script that runs real services follows the same rule.

### Build exception

The usual rule of not running a build does not apply here. Every Node template is built during verification, because a template has no deploy pipeline that would catch a broken build.

### Script contract every template must meet

- Node templates define the scripts `lint`, `format:check`, `typecheck`, `test` (single run, never watch mode) and `build`, and carry `.nvmrc`. `check-template.sh` fails when a script is missing; the allowlist at the top of the script is empty.
- Web templates, with or without an overlay, also define `test:e2e`, a Playwright run that starts the app itself, and ship error and not-found pages through `shared/components/ErrorState.tsx`, `src/test/renderWithProviders.tsx` and `src/test/matchMedia.ts`.
- Every web project has `shared/hooks/useNotification.ts` with exactly the methods `success`, `error`, `warning` and `info` and a test that guards them. The plain base's version needs no dependency. A UI overlay replaces it with the library's own, at the same paths, so no plain file is left beside it.
- Every UI overlay provides `shared/providers/UiProvider.tsx`, that hook, `shared/styles/theme.ts`, a Home page rendered through the library's own component, a Playwright spec that asserts a computed style only that library's stylesheet produces, and the documents `docs/rules/ui.md`, `docs/styles.md`, `docs/components/README.md` and `docs/components/useNotification.md`. An overlay overwrites a base file only where the library needs it, so the base stays the shared truth.
- Node servers also define `start`, which runs the built output and listens on port 8000. A base boots with no `.env` and an empty environment; a server with a required setting refuses to start without it or with a value it cannot read, naming the variable and never a value.
- Every server ships the `src/infra/` seam. Its dependency checks run before the server listens, and a failed check exits non-zero naming the check, never a value. The health route answers through one shared probe: 200 `{"status":"ok"}` when every check passes, 503 `{"status":"unavailable"}` otherwise. The test runner loads the fake values of `.env.example` and the ordinary tests replace the seam with one that has no checks, so `pnpm test` and `make test` need no service.
- Every template but `workspace` ships a `Dockerfile`, a `docker-compose.yml` and a `.dockerignore`. The compose file starts with `name: ${COMPOSE_PROJECT_NAME:?...}`, and so does `docker-compose.dev.yml`. A backend has a service `server` that answers `GET /api/health` on port 8000 inside its container and runs as uid 1000. A web base has a service `web` that reads no `env_file`, answers `GET /` and publishes `WEB_PORT` on loopback: Next.js runs as uid 1000, and Vite serves from the unprivileged nginx image as uid 101. No image takes a build argument but `API_HOST` and `PART`, and none holds a secret. A Node image takes its major version from `.nvmrc`, and only the final stage's `USER` counts. A data overlay with a database adds a one-shot service `migrate` (the server's image, `restart: 'no'`) that `server` waits for with `service_completed_successfully`, passes the store's URL to both from the service name, blanks the `TEST_*` URLs in both, and a PostgreSQL overlay adds `docker-compose.postgres-cluster.yml`. `test-render.mjs` guards these over the real output and `check-docker.sh` over the built image.
- The `workspace` template builds its `contract` package to `dist`, exports it through an `exports` map, and exports `helloResponseSchema` (a zod schema); `live-check.sh` imports it from Node. Its root defines `prepare` (builds `contract`) and `dev` (runs every package's `dev`, in parallel).
- FastAPI templates define the Makefile targets `lint`, `format-check`, `typecheck` (optional), `test` and `start`, using hyphenated names because a colon in a target name is not valid. They use `uv` and commit `uv.lock`. A FastAPI data overlay adds `test-integration` and, for a SQL store, `db-generate`, `db-migrate` and `db-status`; its models live in `src/db/models/`, its migrations in `alembic/versions/`, and `db-migrate` and `db-status` print no host, user or path when the database cannot be reached.
- Every template has its own `.gitignore` that covers `.env`.

### Live behaviour of servers

Every route is under `/api/v1/` except the health route. `GET /api/v1/hello` answers exactly `{"success":true,"payload":{"data":{"message":"hello world!!"}}}`, and `GET /api/health` answers 200 with exactly `{"status":"ok"}`, outside the envelope. An unknown route answers 404 with `success` false and a string `payload.message`. `live-check.sh` refuses to run when port 8000 is taken.

Every server limits requests per client by default: 300 per 60 seconds, from `RATE_LIMIT_MAX` and `RATE_LIMIT_WINDOW_SECONDS`, keyed on the socket address unless `TRUST_PROXY` names the proxies in front. A request over the limit answers 429 in the failure envelope, and the health route is exempt. The counts live in process memory, and in a Redis overlay they live in Redis, shared by every instance: a Redis that does not answer within a second answers the request 503 in the failure envelope and never lets it through uncounted.

## monorepo.sh

`monorepo.sh <project> <next|vite> <plain|antd|mui|heroui> <nest|fastify|fastapi> [--dashboard <next|vite> <plain|antd|mui|heroui>] [--data <store>[,redis]] [--no-docker]` is the only composed form, and what it leaves on disk must be a project that runs once the steps it prints are done. Rules for the script:

- It is piped to bash, so everything is a function and the last line calls them: a truncated download runs nothing.
- It validates every argument before writing anything, and refuses with exit 2, an existing target included; only a failure after validation (a download, a missing tool, a target that appeared meanwhile) exits 1. The project name matches `^[A-Za-z0-9][A-Za-z0-9._-]*$`, so a path cannot escape, and an existing target is refused. `--dashboard`, `--data` and `--no-docker` come in any order after the four words and at most once each; `--data` needs a value and accepts exactly `postgres`, `sqlite`, `mysql`, `redis`, `postgres,redis`, `sqlite,redis` and `mysql,redis`, in that spelling and order, and `fastapi` refuses the two with `mysql`.
- It composes in a temporary directory beside the target and moves it into place only on success. It never installs and never runs `git init`; it prints the next steps.
- `PROJECT_TEMPLATES_ARCHIVE` points it at a local archive instead of downloading one; verification uses it.
- It extracts the `workspace` template at the root, each web base into `web/` (and `dashboard/`) with `--strip-components=3`, the chosen overlay over it unless the choice is `plain`, and the server into `server/`. With `--data` it then extracts `overlays/<server>-<choice>` (the comma becomes a dash: `nest-postgres-redis`) over `server/`. It deletes every lockfile the Node parts brought and their nested `pnpm-workspace.yaml`, so the first install writes one lockfile for the composed tree; the root `pnpm-workspace.yaml` carries the union of the build-script allowlists, `better-sqlite3` included. `fastapi` keeps its `uv.lock`.
- It renames the parts to `web`, `dashboard` and `server` in their `package.json`. With a Node server it adds `"@app/contract": "workspace:*"` to every part.
- A dashboard's ports are moved off the web app's so both run at once: 3000, 3100, 5173, 4173 and 5273 become 3001, 3101, 5174, 4174 and 5274 in its scripts, configs and documents, so its documents state the ports it really uses.
- With `fastapi` there is no contract package: it removes `contract/` and `docs/contract.md` and extracts the `workspace-no-contract` overlay over the root. The workspace file lists only the web apps, and the root documents say there is no contract.
- A composed part keeps its own `AGENTS.md` and `CLAUDE.md`; `CLAUDE.md` is always the one line `@AGENTS.md`. `contract/` has no `CLAUDE.md`.
- A server with a store refuses to start without its settings and its services: the startup check is a `select 1`, not a probe of the tables, so a server whose database has no migrations starts and answers health 200, and its queries need the migration. A SQLite file is the exception: only a migration creates it, so until then the server refuses to start. With `--data` the next steps therefore copy `server/.env.example` to `server/.env`, start `server/docker-compose.dev.yml` when the choice has a server store, and migrate when it has a database, all before the dev command. The compose file sits in `server/`, which compose would take as the project name, so two projects on one machine would share containers and volumes, and `down -v` could delete another project's data; the commands in the compose file's header and the printed command name the project (`-p`, in lower case with dots as underscores) instead.

### The Docker side of a composed project

- The call `pt_docker_root` extracts `scripts/` and `source/` from the archive into its work directory and runs `docker-blocks.mjs monorepo`, which reads the data overlay's layers from `recipes.mjs` of the same archive, so the join is one implementation and no store's name enters `monorepo.sh`. It writes the root `docker-compose.yml` (one block per web framework from `source/docker/monorepo`, instantiated for `web` and `dashboard` with `PART` and their port variables, then the server block and the overlay's store blocks; `migrate` builds the server's image), each part's monorepo `Dockerfile` (the build context is the root, and a Vite part also gets the nginx template with Docker's DNS resolver), the root `.dockerignore` and the root `.env.example`. A FastAPI server keeps its own `Dockerfile` and `.dockerignore`, whose context is `server/`. A cluster compose file moves to the root, and each part's standalone `docker-compose.yml` and `.dockerignore` are removed.
- The lines of every `env.fragment` under `source/docker/` leave each part's `.env.example`, and so do `COMPOSE_FILE`, any `*_DOCKER_NETWORK` line and the comment directly above each, found by those names so no store's name enters the code. The root `.env.example` holds the block of `source/docker/monorepo` (`COMPOSE_PROJECT_NAME` filled with the compose name, `EDGE_SUBNET`, `TRUST_PROXY`, `WEB_PORT` and with a dashboard `DASHBOARD_PORT`), the server's lines and the moved ones. No part keeps a line nothing reads. The root `.env` is what compose interpolates and the `env_file` of `server` and `migrate` alone; `server/.env` serves a server run on the host. A composed root needs a lockfile, which the printed `pnpm install` writes before the printed Docker line.
- `web` and `dashboard` read no `env_file` and sit on the `edge` network with `server`; the stores stay off it, and `server` publishes no port. `EDGE_SUBNET` is `10.<a>.<b>.0/24` derived from the compose name with `cksum`, and `TRUST_PROXY` is the same value, so the server believes the visitor address a web part forwards and no peer off `edge`. Next passes the header through and nginx keeps an existing one, so a visitor reaching a web port directly could choose a bucket: web ports publish on loopback, and a proxy in front is needed to open one.
- `--no-docker` writes none of those root files, deletes each part's `Dockerfile`, `docker-compose.yml` and `.dockerignore` and any `docker-compose.*-cluster.yml`, takes the same lines out of each part's `.env.example`, and keeps `docker-compose.dev.yml`. The `workspace` template fetched alone has no parts and ships no Docker files.

## Documents

- `AGENTS.md` files and everything under `docs/rules/` are English and contain no CJK characters.
- Every other page under `docs/` is Traditional Chinese.
- Root `docs/` of a monorepo holds product rules; `web/docs/`, `dashboard/docs/` and `server/docs/` hold implementation rules and records. `docs/README.md` of the workspace states the split and indexes what ships.
- Relative links must resolve, and a root document links into a part only through code spans, because the standalone `workspace` fetch has no parts. `check-docs.mjs` enforces the language split, the links, the required paths per template type, and the `.env` ignore.
- Records state only what exists: indexes list what ships, nothing planned. Every backend ships the store-neutral rules in `docs/rules/data.md`, written as a rule and never as a record: Node projects use Drizzle for schema and migrations, FastAPI projects use SQLAlchemy and Alembic. A store's own rule page ships with its data overlay, and `check-docs.mjs` requires `data` and no store page.

## Rules for contributors

- Node standard library only for `.mjs` scripts; bash 3.2 compatible for `.sh` scripts (macOS).
- Code comments and docstrings are English; JSDoc on functions.
- Nothing in the repository may name a private project, host or person. The repository is meant to be public.
- Commits follow Conventional Commits and are written in English.
